# CLAUDE.md — Salesforce Mobile SDK UI Tests

---

## About This Project

This repository contains end-to-end UI tests that validate apps generated by the Salesforce Mobile SDK CLI tools (`forceios`, `forcedroid`, `forcehybrid`, `forcereact`). Tests run against real generated apps on simulators/emulators or physical devices, covering the complete login flow, SDK auth variants, and upgrade scenarios.

**For user-facing overview and quick start**: See [README.md](README.md)

**Key constraint**: These tests exercise the **public-facing behavior** of the SDK. They catch regressions in the auth flow, token handling, and app generation that unit tests cannot catch.

## TestOrchestrator Architecture

The `TestOrchestrator` is a Kotlin CLI application (compiled to a binary named `test`) that drives the full end-to-end flow:

| Source File | Responsibility |
|-------------|---------------|
| `Main.kt` | CLI entry point — parses args via Clikt, dispatches to TestRunner |
| `TestRunner.kt` | Orchestrates the generate → compile → install → test pipeline |
| `AppGenerator.kt` | Calls `SalesforceMobileSDK-Package` CLI tools to generate apps |
| `AppCompiler.kt` | Builds generated apps (xcodebuild for iOS, Gradle for Android) |
| `AppInstaller.kt` | Installs compiled apps on simulator/emulator/device |
| `AppInfo.kt` | Data model for app type, platform, and generated paths |
| `AppUpgrader.kt` | Handles the upgrade testing flow (old SDK → dev SDK) |
| `util/CommandUtil.kt` | Shell command execution helpers |
| `util/CIRuntimeInstaller.kt` | Downloads/installs iOS simulator runtimes in CI |

**Shared source**: `shared/src/kotlin/com/salesforce/UITestConfig.kt` is compiled into both the orchestrator and the Android test APK. It defines the `UITestConfig`, `LoginHost`, `User`, `AppConfig`, and enum keys (`KnownUserConfig`, `KnownLoginHostConfig`, `KnownAppConfig`) that map to entries in `ui_test_config.json`.

## Build & Run Commands

```bash
# Initial setup — clones SalesforceMobileSDK-Package for app generation
./install.sh

# Compile TestOrchestrator after making source changes
./compile.sh

# Run with Gradle directly (faster for development, no need to recompile)
./gradlew :TestOrchestrator:run --args="android native"

# End-to-end: generate, build, and test a native Android app
./test android native

# Test multiple app types at once
./test android native native_kotlin hybrid_local react_native

# Test on iOS (creates and destroys simulator automatically)
./test ios native_swift --ios=18.5

# Upgrade test: generate with old SDK, login, upgrade to dev, verify session survives
./test android MobileSyncExplorerKotlin --upgrade=12.1.0
./test ios MobileSyncExplorerSwift --upgrade=12.1.0 --ios=26

# Re-run tests without regenerating apps
./test android native --reRun

# Preserve previously generated apps (skip cleanup)
./test android native --preserverGeneratedApps

# Use SF CLI (sfdx) for app generation instead of standalone tools
./test android native --sfdx

# Run Android tests in Firebase Test Lab (CI default)
./test android native --firebase=true

# Verbose output (always on in CI)
./test android native --verbose
```

### Running Android Tests Directly (without orchestrator)

```bash
# After a generated app is installed:
adb shell am instrument -w -r \
  -e debug false \
  -e packageName com.mycompany \
  com.salesforce.mobilesdk.mobilesdkuitest.test/android.support.test.runner.AndroidJUnitRunner
```

### Running iOS Tests Directly (without orchestrator)

```bash
xcodebuild -scheme MobileSDKUITest \
  -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone SE (3rd generation),OS=18.5' \
  TEST_APP_BUNDLE='com.salesforce.App-native-ios' \
  test
```

## Test Configuration

Both platforms require a `ui_test_config.json` before tests can run.

**Setup:**
```bash
cp shared/test/android/ui_test_config.json.sample shared/test/android/ui_test_config.json
cp shared/test/ios/ui_test_config.json.sample     shared/test/ios/ui_test_config.json
# Edit both files — fill in real consumer keys, redirect URIs, and passwords
```

The config defines:
- **loginHosts**: Named Salesforce org URLs with test user accounts (`REGULAR_AUTH`, `ADVANCED_AUTH`)
- **apps**: Named OAuth app configurations (`ECA_OPAQUE`, `ECA_JWT`, `BEACON_OPAQUE`, `CA_OPAQUE`, etc.)

`UITestConfig.kt` loads the config from `shared/test/<platform>/ui_test_config.json` (local) or `/data/local/tmp/ui_test_config.json` (on-device for Firebase Test Lab).

**Config never goes in source control.** The `.sample` files are the canonical reference; the real config files are gitignored.

## Android Tests

**Framework**: UIAutomator 2 via AndroidX Test (instrumentation tests in `Android/app/src/androidTest/`)

**Test classes:**
- `LoginTest.kt` — standard WebView-based OAuth login (regular + advanced auth, ECA, CA, JWT variants)
- `NativeLoginTest.kt` — native login UI flow
- `UpgradeTest.kt` — validates session survival across SDK version upgrade

**Page Object pattern**: All UI interaction goes through page objects in `PageObjects/`:
- `LoginPageObjects/LoginPageObject.kt` — WebView login screen
- `LoginPageObjects/AuthorizationPageObject.kt` — OAuth authorization screen
- `LoginPageObjects/NativeLoginPageObject.kt` — Native login screen
- `TestAppPageObjects/NativeAppPageObject.kt` — Post-login native app screen
- `TestAppPageObjects/HybridAppPageObject.kt` — Hybrid (Cordova) app screen
- `TestAppPageObjects/ReactNativeAppPageObject.kt` — React Native app screen
- `TestAppPageObjects/MobileSyncKotlinAppPageObject.kt` — MobileSync template app screen

**Android build details:**
- Language: Kotlin
- Minimum SDK: 31 (Android 12)
- Firebase Test Lab: used in CI for parallel execution across API levels

## iOS Tests

**Framework**: XCUITest (`iOS/SalesforceMobileSDK-UITest.xcodeproj`)

**Test classes** (in `iOS/Tests/`):
- `LoginTest.swift` — standard OAuth login flow
- `NativeLoginTest.swift` — native login UI flow
- `UpgradeTest.swift` — session survival across upgrade

**Page Object pattern**: All UI interaction in `iOS/PageObjects/`:
- `LoginPageObjects/` — Login screen, authorization screen, native login screen

**iOS build details:**
- Language: Swift
- Minimum target: iOS 18.0
- Simulators are created and destroyed automatically by the orchestrator during local runs

## Code Standards

### Kotlin (TestOrchestrator + Android tests)
- Kotlin for all new code. No new Java files.
- Follow the existing Page Object pattern — never add raw `UiDevice`/`UiSelector` calls in test classes.
- Use suspending functions and coroutines for async operations in the orchestrator.
- Null safety: avoid `!!` without clear justification.

### Swift (iOS tests)
- Swift for all new code. No new Objective-C files.
- No force unwraps (`!`).
- Follow the existing Page Object pattern — never add raw `XCUIElement` queries in test classes.

### General
- **No hardcoded credentials** in source. All auth data lives in `ui_test_config.json` (gitignored).
- **Tests must be deterministic**: no hardcoded sleeps. Use proper UIAutomator/XCUITest wait APIs.
- **Clean up after tests**: leave the device/simulator in a logged-out state for the next test.
- **Page Objects own selectors**: if a UI element changes, the fix goes in the Page Object, not the test.

## Code Review Checklist

When reviewing PRs (or acting as an AI reviewer), verify:

- [ ] **No credentials in source**: No usernames, passwords, consumer keys, or org URLs hardcoded.
- [ ] **Page Object pattern followed**: UI selectors in Page Objects, not test classes.
- [ ] **Both platforms considered**: If fixing a test pattern, is the equivalent fix needed on the other platform?
- [ ] **Deterministic**: No `Thread.sleep()` or hardcoded delays. Uses proper wait/timeout APIs.
- [ ] **Orchestrator still compiles**: Run `./compile.sh` after changes to `TestOrchestrator/` or `shared/`.
- [ ] **Config sample updated**: If the config schema changes, `ui_test_config.json.sample` must be updated too.
- [ ] **CI workflow unbroken**: `.github/workflows/nightly.yaml` still reflects how tests are invoked.

## Agent Behavior Guidelines

### Do
- Before running tests, verify `shared/test/android/ui_test_config.json` and `shared/test/ios/ui_test_config.json` exist (they are gitignored and must be created locally).
- After modifying any file under `TestOrchestrator/src/` or `shared/src/kotlin/`, run `./compile.sh` to verify the binary compiles.
- When adding a new test scenario, add the corresponding enum value to `UITestConfig.kt` if a new named app or user config is needed.
- Use the Gradle direct invocation (`./gradlew :TestOrchestrator:run --args="..."`) during development to avoid recompiling unnecessarily.
- When diagnosing a test failure, check whether it's an orchestrator issue (app generation/compilation) or a test harness issue (UIAutomator/XCUITest).

### Don't
- Don't hardcode org URLs, usernames, consumer keys, or redirect URIs anywhere in source files.
- Don't add `Thread.sleep()` or hardcoded delays in test or page object code.
- Don't bypass the Page Object layer by calling UIAutomator/XCUITest APIs directly in test classes.
- Don't modify `install.sh` or `.github/workflows/nightly.yaml` without explicit human request.
- Don't commit `ui_test_config.json` (it's gitignored and may contain credentials).

### Escalation — Stop and Flag for Human Review
- Any change to how OAuth credentials are loaded or passed to the test app.
- Changes to the upgrade test flow (`AppUpgrader.kt` or `UpgradeTest`).
- Modifications to `nightly.yaml` CI workflow.
- Changes to the `UITestConfig` schema that break backward compatibility with existing config files.
- Adding new external service dependencies to the orchestrator.

## Key Domain Concepts

- **TestOrchestrator**: The compiled Kotlin CLI (`test` binary) that drives the full generate → compile → install → test pipeline. Source lives in `TestOrchestrator/`; rebuilt with `./compile.sh`.
- **Page Object**: A class that encapsulates all UI element selectors and interactions for one screen. Tests call Page Object methods; they never query UI elements directly.
- **ui_test_config.json**: Gitignored JSON file that supplies login host URLs, test user credentials, and OAuth app configs (consumer key + redirect URI) to both the Android instrumentation tests and iOS XCUITests. Must be set up locally before running tests.
- **KnownAppConfig / KnownUserConfig / KnownLoginHostConfig**: Enums in `UITestConfig.kt` that are stable keys used in test code to reference entries in `ui_test_config.json`. Add new entries here when new app or user configs are needed.
- **Firebase Test Lab**: Google's cloud device farm used in CI to run Android tests across multiple API levels simultaneously. Triggered by `--firebase` flag; requires the test APK and app APK to be uploaded.
- **Upgrade test**: A multi-phase test that generates an app with an older SDK version, logs in, then reinstalls with the dev SDK (preserving app data) and asserts the user is still logged in — validating session token migration.
- **Advanced Auth**: OAuth login flow that uses the device's native browser (Custom Tabs on Android, ASWebAuthenticationSession on iOS) instead of a WebView. Tested against a separate org (`advanced_auth` login host) that requires this mode.
- **ECA (External Client App)**: The preferred Salesforce OAuth app model, replacing the legacy Connected App. `ECA_OPAQUE` and `ECA_JWT` in the config correspond to ECA configurations that issue opaque vs. JWT access tokens.

## CI / Nightly Workflow

Tests run nightly via `.github/workflows/nightly.yaml` against the `master` branch. Status badge is in `README.md`.

CI passes `--firebase=true` for Android (runs on Firebase Test Lab across supported API levels) and creates/destroys real iOS simulators for iOS runs.
